# Проверка и выпуск обновлений

Дата: 2026-11-09. Целевой сервис и версии перечислены в [карте проекта](PROJECT.md).

## Перед изменением кода

1. Проверить реальный корень репозитория, текущий worktree, ветку и Git-статус.
2. Описать нужное поведение и найти его в существующем приложении.
3. Сопоставить рабочую сборку с выбранной базой. Название папки, самая поздняя
   дата файла или надпись `main` не устанавливают состав рабочего релиза.
4. Сохранить незакоммиченные изменения и untracked-файлы каждого источника.
   Их присутствие в соседнем worktree не означает, что они уже сохранены в Git.
5. Переносить функции небольшими проверяемыми изменениями. Сверять также
   миграции: в старом context-repro есть другая миграция с номером `010`.

Из основного каталога в PowerShell:

```powershell
rtk git rev-parse --show-toplevel
rtk git branch --show-current
rtk git status --short
rtk git -c core.quotePath=false worktree list
rtk git diff --stat
```

Не запускать второй экземпляр бота с рабочим Telegram-токеном: два polling
процесса конкурируют за обновления. Для тестов использовать изолированное
окружение. Не запускать `main.py` с рабочими настройками как способ проверки.

## Проверки перед релизом

Источник перечня — [существующий CI](../../.github/workflows/ci.yml).
Команды ниже выполняются в подготовленном тестовом окружении с установленными
зависимостями. Их перечисление здесь не означает, что они выполнены этой уборкой.

```powershell
rtk proxy .\.venv\Scripts\python.exe -m ruff format --check .
rtk proxy .\.venv\Scripts\python.exe -m ruff check .
rtk proxy .\.venv\Scripts\python.exe -m mypy app
rtk proxy .\.venv\Scripts\python.exe -m pytest --cov=app --cov-branch --cov-report=xml --cov-fail-under=80
```

Остальные проверки CI: Alembic upgrade/downgrade/check на **одноразовой тестовой
PostgreSQL**, Bandit, pip-audit, сборка Docker, Trivy и Gitleaks. Не выполнять
проверку downgrade на рабочей базе. Устанавливать зависимости и менять
конфигурацию среды следует только в согласованном объёме.

Для существующих изолированных тестов Sheets доступен runner, который
отключает dotenv, pytest-кэш и внешние подключения:

```powershell
rtk proxy ..\FAMILY-AI-LIFE-OS\.venv\Scripts\python.exe -B scripts/run_offline_tests.py tests/test_google_workspace.py::test_monthly_budget_category_mapping_and_projection_key tests/test_google_workspace.py::test_monthly_budget_projection_sets_formulas_and_verifies_receipt tests/test_google_workspace.py::test_monthly_budget_projection_replay_does_not_append_twice tests/test_google_workspace.py::test_sheet_worker_row_has_stable_transaction_identity -q
```

Runner сохранён в `scripts/` объединённой версии. Здесь используется существующее
Python-окружение исходного worktree. Эти тесты не заменяют остальные проверки релиза.
Полный сырой diff конфигурации и секретные значения в отчёты не копировать.

## Выпуск

Целевой порядок после объединения версий:

1. Выбранный diff просмотрен; проверки относятся к точному выпускаемому коду.
2. После явного поручения — selective staging и commit. Записаны commit и
   результаты проверок. `commit + push` не подразумевает разрешения на deploy.
3. После отдельного явного поручения — выкладка этого commit/артефакта в
   существующий сервис Railway, без подмешивания файлов других worktree.
4. Записаны deployment ID, исходный commit, состав пакета, результаты smoke
   checks и предыдущий deployment для отката.

Сейчас этот порядок документирован, но автоматический deploy и GitHub-настройки
не менялись. Перед push нужно проверить фактическое поведение Railway-триггеров.
В прошлом локальные исправления выпускались пакетами без коммита; повторять
такой выпуск без полного манифеста состава не следует.

В `.dockerignore` исключены `outputs` и `.worktrees`. Это ограничивает контекст
Docker-сборки, но не заменяет проверку состава загрузки Railway CLI: архив
для выкладки должен собираться из явно выбранных исходников, без диагностики,
копий данных и соседних worktree.

При изменении только месяца/таблицы загрузка локального исходного кода не нужна:
применить согласованные настройки к той же проверенной сборке и проверить
синхронизацию по [инструкции Sheets](MONTHLY_SHEETS.md).

## Проверка после выкладки

- Deployment имеет статус `SUCCESS`; публичные `/live` и `/health` отвечают.
  Эти ответы сами по себе не доказывают исправность Sheets/Oura.
- Один активный Telegram polling; в логах нет продолжающихся конфликтов.
- Для финансовых изменений: точные UUID, даты, суммы и категории совпадают с
  PostgreSQL, служебной вкладкой и видимым бюджетом; повторных UUID нет.
- Для Oura/Google: проверить именно изменённый путь. Сообщения людям и тестовые
  записи с реальными данными требуют соответствующего поручения.

При необходимости отката сначала установить, менялась ли схема или данные.
Откат приложения не откатывает автоматически PostgreSQL или Google Sheets.
Возврат старого deployment и любые изменения базы — отдельные согласованные
действия; автоматического удаления данных здесь нет.

## Что проверено при уборке

- Прочитаны локальные Git-метаданные, исходники и описание deployments Railway.
- В предшествующем аудите четыре существующих теста Sheets прошли.
- Проверки новых документов, скрипта инвентаризации и сохранности runtime-файлов
  выполняются отдельно. Полный CI и интеграционные миграции этой уборкой не запускались.
